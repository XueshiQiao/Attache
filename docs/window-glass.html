窗口毛玻璃：三种做法，
以及公开 API 为什么只能给你一半

「半径可调」和「Metal 图层底下也有效」是两件事。macOS 的公开接口每次只给一件， 而一个终端两件都需要——这份笔记记录三种实现各自是什么、差在哪，以及最后为什么落在一个私有符号上。

1 · 症状：一个窗口里有三种玻璃

第一版做完，报回来的现象是「一个窗口里三种风格，受不了」。这不是审美分歧，是三块区域真的由三套不同的东西画的， 而当时那个「透明度」滑块只控制得了其中一层色。

图 1. 三块区域分属三个所有者，其中两个属于 AppKit。「调透明度」只作用在最上面那层色， 所以滑块拉到 15% 时窗口仍然几乎不透——被挡住的不是色，是底下的材质。
核心事实

macOS 的「材质」（NSVisualEffectView）不是一块可以透过去看的玻璃， 而是一块自带不透明度的磨砂板。在它上面刷再淡的色也减不掉它自己的密度， 它的模糊量则是 Apple 按材质写死的，没有任何接口可以改。

2 · 三种机制，本质上不是一回事

三种做法把「透明」「模糊」「颜色」放在了不同的位置，所以它们不是同一个东西的三档参数， 而是三套机制。任何一个绘制点如果自己去猜，就会把其中一样上两遍。

风格机制模糊半径Metal 图层底下私有 API

窗口服务器给整窗背景加模糊		 任意可调 有效 是

macOS 26 的原生玻璃，自带 tintColor		 系统决定 有效 否

最后一行是这份笔记存在的原因：它是唯一一个「公开 + 半径可调」的组合，而它在这个 app 里不能用。

3 · 为什么 backdrop 滤镜够不到 pane

CALayer.backgroundFilters 在 macOS 上是公开的，语义是「把这一层背后的东西过一遍滤镜」。 问题在于每个 pane 是 libghostty 的 Metal 图层，被单独合成在那一层之上—— 透过 pane 看到的桌面根本没有经过这个滤镜。

图 2. 差别不在效果强弱，在模糊什么时候发生。滤镜是合成时对 backdrop 求值， 所以任何单独合成的图层都会绕过它；后两种是把模糊变成一张已经存在的内容，绕不过去。

现场表现完全对得上：拉动半径时窗口边缘、标题带、侧栏在变，中间被 pane 盖住的地方纹丝不动。 这不是参数没调对，是这条路走不通。

4 · Ghostty 是怎么做的

参照物是 Ghostty（截图里那台叫 Otty，同族）。它的配置里有 background-blur = <强度>， 默认 20；在 macOS 26 上还多两个特殊值 macos-glass-regular 和 macos-glass-clear。 两条路它都走了。

第一次去它二进制里找，用 strings 扫「CGS」「SkyLight」一无所获，差点得出「它没用私有接口」的结论。 真正的位置是导入表：

# strings 扫不到，nm 一眼就看到
$ nm -u /Applications/Ghostty.app/Contents/MacOS/ghostty | grep CGS
_CGSDefaultConnectionForThread
_CGSMainConnectionID
_CGSSetWindowBackgroundBlurRadius
教训

符号名住在导入表里，不在字符串段。strings | grep 扫不到不能说明一个 app 没有调用它—— 要用 nm -u 看未定义符号。这一步差点让整条结论反向。

这三个符号是 CoreGraphics 正常导出的，Ghostty 直接链接。这是窗口服务器级别的模糊， 所以既能任意调半径，又完全不在乎窗口里画的是不是 Metal——正是公开 API 给不了的那个组合。

我们的接法：dlsym 而不是直接链接

// 直接链接的话，哪天系统拿掉这个符号，app 会启动就崩。
// 运行时解析，同样的系统只是没模糊。
private static let entryPoints = {
    guard let c = dlsym(RTLD_DEFAULT, "CGSMainConnectionID"),
          let r = dlsym(RTLD_DEFAULT, "CGSSetWindowBackgroundBlurRadius")
    else { TmuxLog.lifecycle("窗口服务器模糊不可用"); return nil }
    return (unsafeBitCast(c, …), unsafeBitCast(r, …))
}()

整个私有调用只有一个文件、一次调用。另外两种风格不碰任何私有接口， 所以「打开它」的那个开关同时也是「关掉它」的开关——要上架 App Store 就切到另外两种。

5 · Liquid Glass 是 macOS 的，不是 libghostty 的

一个容易搞混的点：NSGlassEffectView 是 macOS 26 AppKit 的公开类， 和 libghostty 没有关系。libghostty 只负责渲染终端网格（那些 Metal 图层）， 窗口的玻璃从头到尾是 AppKit 的事。

// MacOSX26.5.sdk/…/AppKit.framework/Headers/NSGlassEffectView.h
@interface NSGlassEffectView: NSView
@property (nullable, strong) __kindof NSView *contentView;
@property CGFloat cornerRadius;
@property (nullable, copy) NSColor *tintColor;   // ← 它自己会上色
@property NSGlassEffectViewStyle style;        // regular / clear
@end

最后那行注释是坑：它自己会 tint。如果绘制点再刷一层同样的颜色， 同一个色就上了两遍——这正是「选了 clear 玻璃却看起来像实心窗口」的成因。

顺带：那圈 Liquid Glass 镶边

侧栏原本用的是 NSSplitViewItem 的 sidebar 模式，它在 macOS 26 上会把侧栏画成一块内嵌圆角面板， 并且给面板的内嵌边距镶一圈 Liquid Glass。那圈镶边就是图 1 里的 ①：它属于 AppKit 拥有的边距， 盖不住、调不了、关不掉。侧栏因此改成齐边到底。

不要改回去

项目历史上这块内嵌面板被「修」坏过两次——为了把红绿灯挪进面板而删掉它，结果红绿灯跑到了面板上方。 这次去掉面板不是那个错误：窗口带 .fullSizeContentView，齐边之后红绿灯仍然浮在侧栏上。 下次想动之前，先看红绿灯实际在哪。

6 · WindowGlass：一处决定，三处询问

三套机制把颜色放在不同位置，所以绘制点不能自己判断。 WindowGlass.resolved() 是唯一做决定的地方，每个绘制点问它要颜色， 在「已经有别人上色了」的情况下拿到的是 .clear。

图 3. 抽象存在的理由不是整洁，是避免三个文件里各写一遍条件判断—— 其中任何一处判断错，症状都是「颜色深了一倍」或「模糊没了」，而且看不出是谁干的。

7 · 设置项：哪个旋钮属于哪种风格

三个通用旋钮 + 每种风格一个自己的。设置界面按当前风格显示对应那一个， inspector 的 /settings 路由能全部实时驱动（Debug 版、仅回环）。

旋钮范围属于作用
windowOpacity0 – 1通用在透出来的结果上再刷多少终端自己的颜色。100% = 实心窗口，也是零开销的那一档

拿掉…症状严重程度

切走风格时不再发 blurRadius = 0 半径存在窗口服务器那边的窗口上，不在进程里。切到别的风格后模糊会一直留着 中

9 · 没有验证的部分

说清楚比含糊过去重要：这三种风格具体长什么样，写代码的人一次都没看见。

app 自己的截图路由用 CGWindowListCreateImage，它只合成那一个窗口、不合成窗口背后的桌面—— 所以在半透明窗口上拿到的是材质「没有背景可采样」时的兜底灰：把窗口挪开一千点再拍，256 级里只差 1 级。 screencapture 能拍到真实合成结果，但需要屏幕录制权限，而 agent 所在的 shell 没有。

能验证的都验证了：四种配置都能正常绘制、侧栏和内容区颜色不同、文字在、冒烟测试通过、 私有符号解析成功（启动日志有一行 window-server blur available）。 「好不好看」这一项，只有人能签字。
