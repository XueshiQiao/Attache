Noticing that nothing happened

Every failure this app had today was silent. It sent the command, drew the old picture, and waited — and only a person staring at it could tell. This adds the missing half: the app checks that what it asked for actually happened.

1 · Why

Three separate faults surfaced on 2026-07-29. Every one of them presented to the user as “the app is broken” and took hours to name, because none of them said anything:

  • A hook-produced reply block stole another command’s completion, so list-windows returned early on an empty parse — a silent return — and the window list froze on a pane tmux had already left.
  • focusPane then re-sent select-pane for a pane tmux had already selected. tmux answers a no-op with silence, so the mirror was never corrected and the keyboard was pulled back to the stale pane after every click.
  • An unrelated tool pulled application activation away on every select-pane. The app was healthy: rendering, tracking the mouse, main thread idle. It simply was not the active application, and nothing recorded that.
The point

The user should not have to describe a symptom, and the agent should not have to guess what the description meant. The app knows what it asked for. It should notice when it does not get it.

2 · Two layers that do not know about each other

Notification is a presentation concern the app will want for many things. Diagnostics is a detection concern. Keeping them apart is what lets either one grow without touching the other, and lets diagnostics be tested with no window on screen.

Figure 1. The orange boundary is all the new code. The app pushes four kinds of fact across it and is told nothing back — diagnostics has no way to change behaviour, which is what makes it safe to leave on.

3 · Expectations are derived, not registered

The obvious design has each UI action register what it expects. That is exactly the intrusion to avoid: every new action would have to remember to do it, and the memory would rot.

TmuxLog.command() is already the single gate every command passes through — its own documentation says so, and lists the three exceptions. So diagnostics reads the command text and derives the expectation itself. No call site changes; a new pane action gets covered for free.

Expectations are checked whenever the model changes and swept by a timer. The last row is the important one: it is the detector that would have caught the deaf-channel state — 847 commands sent, zero replies — in five seconds rather than in an hour.

4 · Record early, alert late

300 ms is the sensitivity the user asked for and it is right for the log: a false positive there costs nothing and the agent reading it can tell a slow round trip from a real stall. It is the wrong number for a toast, because a toast that cries wolf gets ignored, and an ignored mechanism is worse than none.

Figure 2. One expectation, two thresholds. The log keeps the sensitivity; the screen keeps the signal-to-noise. An expectation met before 300 ms leaves no trace anywhere.

5 · The toast — three options to pick from

Top-right, sliding in, stacking downward, auto-dismissing. All three below are drawn at real size against a dark translucent backdrop so the glass reads honestly. They differ in how much they say before you interact.

Option A — rail-consistent. Reuses the sidebar row vocabulary exactly: 6 pt radius, 12 pt semibold title, 10.5 pt secondary line, severity as a 2 pt edge.

Asked tmux for window 8 · dotfiles. No confirmation after 1.5 s.
tmux stopped answering
Session dev · 41 commands sent, no reply for 6 s.

Option B — banded, with grouping. A header rule separates title from detail, and repeats collapse into a count instead of stacking. Roomier; carries a timestamp.

21:58:04 · session dev
tmux stopped answering
41 commands sent, no reply for 6 s.
21:58:11 · session dev

Option C — one-line ticker. The least the app can say and still be honest. Detail only on click. Cheapest to ignore, which cuts both ways.

Window did not switch — window 8
tmux stopped answering — session dev
Recommendation

Option A. It is the only one that adds no new visual vocabulary — the radius, the type sizes and the accent edge are already on screen in every sidebar row, so a toast reads as part of the app rather than as a system alert wearing its clothes. B’s grouping is worth stealing later if repeats turn out to be common; C hides the one thing worth reading.

6 · What gets written

Two sinks, because they answer different questions. The line is for “did this ever happen”; the snapshot is for “why”.

// ~/Library/Logs/Attache/anomalies.log — one line, greppable
[2026-07-29 21:58:04.311] [EXPECT] [dev] select-window -t @13 unmet after 312ms
    (active window still @9) snapshot=21-58-04-311-expect-window.json

// ~/Library/Logs/Attache/anomalies/<stamp>-<kind>.json — the scene
{
  "tmuxTruth":   { /* list-windows / list-panes, asked at this instant */ },
  "appModel":    { /* what the app believed */ },
  "recent":      [ /* last 200 commands and reply blocks */ ],
  "activation":  [ /* key-window and first-responder transitions */ ]
}

Snapshots are capped at the most recent 20 and pruned on launch. Every anomaly also goes to tmux-commands.log so one file still holds the whole timeline.

Learned today, at a cost of about an hour

The activation array exists because on 2026-07-29 the app looked frozen — no typing, no clicks, no window switching — and was in perfect health. It had merely stopped being the active application, and nothing in the app recorded that it ever had been. One line of transition history would have answered it immediately.

7 · What is deliberately not in scope

Not doingWhy
Auto-recovery — re-sending a command that went unconfirmedRe-sending is exactly what locked the state today. Measure the real rate first; decide what to repair second.
A select-pane dedupeThe reason it mattered (an external tool stealing focus on every hook) is being removed. A redundant no-op costs one round trip.
Anything about the mouse-report volumeToday’s numbers are contaminated by a resize war an external tool amplified. Re-measure on a clean machine before tuning a filter.
The window-size war itselfReal, unwinnable by the current back-off, and a product decision rather than a bug. Separate note.

8 · Failure modes

If this is removed or wrongWhat breaks
Diagnostics can change app behaviourThe observer becomes a participant, and a false positive turns into a real fault. It must be write-only into logs and the toast.
Expectations registered at call sites instead of derivedRots on the first new action nobody remembers to annotate — the failure this design exists to avoid.
One threshold instead of twoAt 300 ms the toast fires on slow round trips and gets ignored; at 1500 ms the log loses the sensitivity that makes it worth reading.
Snapshots unboundedAn anomaly storm fills the boot volume — the thing that reports a problem must not become one.
No “reply block never arrived” probeThe deaf-channel state stays invisible; it is the one failure where every other detector also goes quiet.
