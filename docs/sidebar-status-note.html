TmuxGUI · sidebar status

What the sidebar knows,
and how it knows it

Each window row carries a branch, a change count, and a coloured dot for the coding agent running in it. Three different sources feed those, only one of them is tmux, and the one that caused the most trouble was the one that looked simplest.

1 · Three sources, one row

A row draws three things and no two of them arrive the same way. Keeping that straight is most of the design, because the app's central rule is that tmux owns everything and the GUI owns nothing — and two of these three are not tmux's to own.

Figure 1. The agent's state is the only one of the three that is stored in tmux, as a pane option. That is deliberate: it means a plain tmux attach from any terminal reads the same value, so the GUI is displaying tmux state rather than authoring its own. Git is genuinely external and stays out of TmuxWindow entirely.
The mechanism that made this cheap

refresh-client -B name:what:format subscribes a control-mode client to a format string, and tmux pushes %subscription-changed whenever the value moves. Verified on tmux 3.6a: subscribing emits the current value immediately, several fields can be packed into one subscription, and the rate is capped at once per second. Nothing is polled.

2 · Every mapping, in one place

Claude Code event → state

The hook writes one of four words into @agent_state on the pane it is running in. It finds its own pane through $TMUX_PANE, which tmux exports into every pane and any child process inherits.

Two guards live in the script rather than in the mapping. Events carrying an agent_id were fired by a subagent and are dropped, and so is SubagentStop — a subagent completing is not the turn ending, and letting it through revives a pane that has finished.

State → what you see

One rule underneath all of it: a colour means an agent. Anything neutral is not about an agent and does not want you.

MarkWordMeaning
● blue, filledworkingComputing. Nothing for you to do.
● amber, filledneeds youBlocked — a permission prompt, a question, an MCP elicitation.
● green, filleddoneFinished its turn — your move.
● grey, filled, smallidleFinished, and long enough ago (30 min) to stop being news. Filled, because this is known.
○ grey, hollowunknownAn agent is running and has never reported — its session started before the hook did. Hollow on purpose: a filled dot would claim more than is known.
▪ grey, small—tmux's own activity flag: output arrived in a window you are not looking at. Used to be amber, which is the colour that now means "an agent is waiting for you" — two very different messages in one colour.

A session heading shows the most urgent state among its windows, which matters most when the session is collapsed — otherwise the one thing worth interrupting someone for is hidden behind a disclosure triangle.

An agent's mark is drawn whether or not its row is selected. Only the last line of that table — tmux's activity flag — is hidden on the selected row, and it is hidden because its meaning is "output arrived where you are not looking", which is not true of the row you are looking at. Everything else stays put: a mark that comes and goes as you click around is telling you something, and if it is not, it should not move.

Why ↓ is usually a lie, and what is done about it

git compares against the last fetch, not against the remote. Without one, ↓0 means "nothing known to pull", which reads as "nothing to pull" and is a different claim. Background fetching is off by default; with it off the tooltip says ↓ unknown — last fetch 47m ago. With it on, the wording follows whether that repository is actually being fetched — one whose fetch is refused for credentials is exactly as stale as one with the setting off.

3 · Three defects, and what each one taught

The rail rebuilt 577 times in 30 idle seconds

Hovering flickered and clicks landed on nothing. Two causes, both mine. GitSummary's synthesised == included readAt, a fresh Date per read, so every identical re-read reported a change. And watching .git while running git status inside it is a feedback loop — measured, 5 plain runs produce 14 filesystem events.

Equality is over the drawn fields now, --no-optional-locks reduces the events, and a quiet window after each read closes the rest. 577 → 0, with the repositories still read.

That storm exposed something older: a rebuild destroys every row, so the row under the pointer is replaced by one that does not know it is hovered, and a press on it is orphaned before the release. The rail now skips a rebuild that would draw the identical thing, holds one back while any mouse button is down, and a new row adopts the hover from where the pointer actually is — AppKit reports crossings, and nothing crosses when a row is rebuilt under a still pointer.

Every idle session turned amber

Figure 2. The bug was not in the implementation but in treating one event as one meaning. Three panes were reading needs-input at once, including a session that had just answered normally and was sitting at an empty prompt. The matcher field is the documented way to tell the subtypes apart; the script also checks the payload directly, so sessions already running pick the fix up without restarting.

Upgrading the hook left the broken version behind

The installer appended. When the event list changed — one Notification entry becoming two with matchers — an upgrade would add the new pair and leave the old catch-all entry firing beside them. The stale entry is precisely the one that was wrong, so the upgrade would have been worse than not upgrading. Installing now removes our own entries and rebuilds them: a sync, not an append. Only entries naming our script are touched, so it is still an append as far as every other tool in the file is concerned.

A file four other tools write to

~/.claude/settings.json here carries hooks for Otty, ccpet, code-rules-check and banned-word-reminder, plus statusLine, permissions, enabledPlugins and more. Every write takes a timestamped backup first, preserves every key it does not recognise, refuses a shape it does not understand rather than overwriting it, and is atomic. It resolves symlinks before writing — an atomic write to a symlinked config replaces the symlink with a regular file, and copyItem on one produces a second pointer rather than a snapshot. Both were demonstrated, then fixed.

The mapping above is a judgement call, not a standard — Anthropic documents the events and leaves the state machine to whoever wants one. So it is worth knowing what the alternatives concluded.

Figure 3. The two approaches fail differently. Reading the screen is zero-configuration and gets "your turn" right, but has to be maintained against a UI that changes — which is why herdr ships its rules as updatable manifests. Reading events is stable and works off screen, but Claude Code exposes no way to tell a finished turn from one waiting on an answer, so that distinction has to be inferred and can be inferred wrongly.

5 · The undocumented file that already has the answer

Claude Code writes ~/.claude/sessions/<pid>.json for every live session. It is undocumented, and it contains the state already computed.

{
  "pid": 65435,
  "sessionId": "3d94bec4-…",
  "cwd": "/Users/joey/Code/tmux-gui",
  "version": "2.1.220",
  "kind": "interactive",      // or "bg" — filters background agents in one field
  "status": "busy",            // busy | idle | shell | (waiting — reported, not yet observed)
  "statusUpdatedAt": 1785209457477
}

Every Claude Code pane maps to one of these cleanly — the pane's shell pid has the agent as a child, and the file's cwd matches the pane's project. Measured against the exact case that started this: the row the sidebar was painting amber reads status: idle in the file. Claude Code had the right answer the whole time.

Figure 4. Decided: B. A single source of truth, because two sources that disagree leave no principled way to pick between them — and the file carries only three states, which is fewer than the row needs. The figure is kept as the record of why. Originally the caption read: The undocumented file is the more accurate source and needs no setup; the hook is the documented one and puts the state somewhere every tmux client can see. Running both means the feature degrades rather than disappears when either goes away.

7 · What breaks if you remove each piece

The Notification matcher splitHIGH Every session that has been idle for a minute turns amber. The colour stops meaning "act on this".

Concurrent draining of both pipesMEDIUM A large repository with noisy stderr hangs one of four queue slots permanently, silently.
Pausing while the window is occludedMEDIUM A laptop runs git all day to draw something nobody is looking at.
The idle state (settled)MEDIUM A finished agent eventually reads unknown — the app claiming not to know something it knows perfectly well. This was the first design and it was wrong.

Twice, from two different causes: a neutral dot vanishing into the accent fill, and a visibility rule that fell through to tmux's activity flag — which hides on the selected row. Hiding has to mean something; neither of these meant anything.
