Embedding the whole of tmux as a terminal: an evaluation

This document changed three times in one day. First, “native scrolling cannot be built” vetoed the embedded route; then the owner tried copy-mode scrolling for real and lifted the veto; then Frank’s measurements overturned “every pain has a fix inside the current architecture” — copy mode and popups never reach control mode at all. Current position: prototype first, leaning toward embedding.

1 · The two routes

Route A (today): the app connects through tmux’s control mode (tmux -C attach). In that mode tmux draws nothing and speaks a plain-text protocol instead: each pane’s raw output bytes arrive line by line, and the app parses the layout itself and places every pane on its own libghostty surface. tmux does not paint; the app does.

Route B (the idea): the app runs a plain tmux attach on a pty it manages, letting tmux draw everything itself the way it does in any ordinary terminal — split lines, every pane’s content, its own status line. The whole picture goes into one libghostty surface; the app is a picture frame. The sidebar still needs a read-only control-mode side channel for the session and window lists.

These are exactly iTerm2’s two ways of using tmux: iTerm2’s -CC integration ≈ route A; typing tmux attach inside iTerm2 = route B. Both are proven viable elsewhere; the question is only the trade.

Figure 1. The difference that matters is the middle box: route A's entire complexity (and its entire trap record) concentrates in the protocol layer; route B deletes it wholesale — the price is Figure 2.

2 · Scrolling: the first version’s veto, and why it was lifted

The first version of this document passed a death sentence here, and the mechanism still holds today: under a plain attach, tmux is a full-screen application. History lives in tmux’s own buffer; the screen is repainted in place inside the same rectangle, so the outer surface’s scrollback is permanently empty (Figure 2). What changed is not the mechanism but the judgment — the owner scrolled for real in other terminals and accepted the copy-mode feel.

The “automatic switching” the owner saw is indeed tmux’s behaviour, with one configuration precondition: mouse on. With it on, a wheel over an ordinary program (a shell, a log) enters copy mode automatically and leaves it when scrolled back to the bottom; over a TUI that handles the mouse itself (vim, htop) the wheel is passed through to the program. Checked: the owner’s ~/.tmux.conf has both mouse on and set-clipboard on — so route B’s scrolling should, in theory, feel exactly like attaching from any other terminal. “In theory” is what the prototype exists to remove: it requires our surface to report mouse events faithfully to tmux, and route A’s TerminalReply deliberately intercepts exactly those reports — it must not exist on route B’s path.

Figure 2. Route A's native scrolling is not something done well — it is an architectural byproduct: history streams byte by byte into each surface's own buffer. On route B that buffer is structurally empty, and no amount of implementation effort can fill it.

Also lost by the same cut, recorded for completeness:

  • Per-pane native interaction. Click-to-select-pane, dropping a file onto a specific pane, per-pane context menus — either they lean on mouse on passthrough, or the app computes which pane is under the pointer from cell arithmetic, which reinvites the layout parsing that was just deleted.
  • tmux’s status line cannot be hidden. It draws at the bottom, duplicating the sidebar. Checked (man tmux 3.6a): status is a session option with no per-client switch — turning it off would also strip it from the owner’s plain-terminal attach to the same session, violating the project’s founding rule that the GUI never affects tmux. (But see the grouped-session idea in §5.)
Status update

The first version wrote “route B’s only revival condition is accepting copy-mode scrolling.” That condition was met the same day. The two remaining costs above were thereby promoted from footnotes to deciding factors — see §5.

3 · Honest accounting: what route B was going to buy

Vetoed or not, the attraction is real and deserves to be written down rather than denied:

What it buysDetail
Most of the protocol layer retires Layout parsing, screen replay, keystroke filtering (TerminalReply), rename-string filtering (TmuxRenameString) — the files with the longest trap records in CLAUDE.md stop being needed. In plain mode tmux digests those sequences itself and emits bytes translated for the outer terminal.
All of tmux’s features for free copy mode, search, zoom, display-popup, dragging splitters with the mouse — behaving exactly as in any terminal, at zero implementation cost.
The reply-pairing trap shrinks (Frank’s correction: it does not vanish) The main channel becomes a pty and is naturally ordered, but the sidebar side channel is still control mode — the 587-line TmuxControlClient (host of the %begin-flags trap, never independently reviewed per TODO §6) is precisely the part that stays. Compensation: the side channel can set the client flag no-output (checked to exist, man 3.6a), receiving no %output at all — so the whole 19 MB/s throughput class of problems does not exist on route B.

But note the accounting problem: most of these traps have already been paid for. TODO §0 (four interaction defects) and §4b (the nine-item “state the GUI reconstructed instead of asking tmux” audit) are all closed, and the four most dangerous files each have a rerunnable regression checker (LayoutCheck / ReplyCheck / ScreenReplayCheck / RenameStringCheck). Switching to route B saves future traps while discarding money already spent and guardrails already built — a much worse deal today than it would have been six months ago. (§5 has Frank’s critique of this argument.)

4 · The three pains, re-examined (with Frank’s measurements)

The second version titled this section “each pain’s fix inside the current architecture.” Frank’s measurements overturned the heaviest item, so it is rewritten honestly:

4.1 “The protocol layer is fragile, maintenance is exhausting” — the curve is actually converging

Read the maintenance record as a curve: the traps burst between 07-26 and 07-28, the phase that forced the truths out; each fix left a comment, a CLAUDE.md entry, and (for the four most dangerous files) a rerunnable checker. The remaining risk surface is three things: behaviour changes in future tmux versions, notification types not yet encountered, and the three pieces of code TODO §6 names as never independently reviewed (TmuxControlClient threading, the reply-pairing FIFO’s error paths, closure lifetimes). Work item: do the §6 review. One payment to retire a whole class of worry — two orders of magnitude cheaper than switching architectures.

4.2 “I want tmux’s full feature set” — Frank measured: two items are simply unreachable on route A

The second version claimed “there is a path for each.” Frank attached a control client to an isolated -L server (tmux 3.6a), recorded every byte on the stream, and validated the method with a sentinel (an ordinary-output marker did arrive as %output, so the zeros below are real zeros):

  • copy mode is invisible to control mode. Entering it delivers a single %pane-mode-changed; scrolling around inside it afterwards puts not one byte on the control stream. So “drive tmux’s copy mode” on route A can render nothing — it is not expensive, the data never arrives. The second version’s recommendation (“search via tmux copy mode”) dies with it; rebuilding natively is in turn blocked by libghostty not exposing TerminalSurface.
  • display-popup is equally invisible. -E exits cleanly with nothing renderable on the control stream. No path on route A.
  • zoom is unaffected: still an hour’s work on route A (an affordance that sends resize-pane -Z).

Settlement: of the features the owner asked for, two are unreachable on route A and free on route B. This is the single heaviest weight shift in the whole evaluation.

4.3 “Display fidelity problems” — needs a concrete list

The known fidelity gaps are three: the re-snapshot (capture-pane) keeps yielding while a pane never stops writing; copy-mode state cannot be drawn; and the ESC k class of “tmux dialect vs libghostty dialect” translation gaps may in principle have a next member. On route A these are all fixable bugs, not structural defects — but note that on route B fidelity is perfect by construction, because tmux draws itself. If the fidelity problems the owner has actually seen are outside the three above, that is new information: record the concrete scene (which program, what action, what was seen) and file it.

5 · Conclusion, and the provenance of every claim

The recommendation stands: prototype first — but after review, the scale tips clearly toward route B. Frank (independent technical consultant) read the repository, ran two sets of measurements, and recommends: prototype first, leaning B. His three core reasons: first, two of the requested features are measured-unreachable on route A (§4.2); second, the “paid-for investment = guardrails” argument only covers known trap classes, and control mode is the least-trodden path in tmux’s user base while plain attach is the most-trodden — the expected count of unknown traps itself favours B; third, B fits this repository’s first principle (“tmux owns everything”) better than A does — A is, in practice, a reimplementation of tmux’s compositor inside the app.

Frank’s reservation (kept verbatim in substance)

His own strongest counter-argument: a few minutes of scrolling in another terminal is not the same as permanently losing native scrolling in a daily-driver tool. If that flips back, route B returns to the first version’s death sentence. So the prototype must not be a demo — build it to daily-usable, use it for days, then decide.

He also corrected the prototype’s construction: no self-managed pty needed — the vendored package has an .exec backend (ghostty forks the child and owns the pty itself; mouse, wheel and resize behave exactly as in Ghostty.app). Re-verified in this session after the second version wrongly claimed “only .inMemory exists” (a search mistake): TerminalSessionBackend.swift:9 declares case exec, it is the default in TerminalSurfaceOptions.swift:23, it maps to GHOSTTY_SURFACE_IO_BACKEND_EXEC in TerminalController+Surface.swift:85, and per-surface envVars is public. The prototype can be a window behind the existing app’s Debug menu (same font, same theme, side-by-side with route A) — with Frank’s warning attached: that is a prototype shape only; once decided, converge on one rendering path, no user-visible dual mode.

What the prototype must answer (as amended by Frank)

  • Does the attach come up at all — the first gate is terminfo: under .exec, TERM=xterm-ghostty, an entry installed by Ghostty.app and not guaranteed present; tmux refuses unknown TERMs. ghostty’s term configuration key can downgrade it (inferred, untested).
  • Scrolling feel — consistent with what the owner felt in other terminals. The foundation of the whole trade.
  • Actually use copy-mode search and display-popup inside the embedded surface — these two are the motive itself, and must be used by hand, not merely shown to render.
  • Sidebar ↔ embedded-client linkage — click a row → select-window → the picture follows; and the reverse, a prefix switch → the rail follows. All of route B’s new seams live on this edge.
  • Status-line experiment: grouped sessions — Frank’s third path (new-session -t creates a shadow session in the same group: windows shared, session options independent, so status off on the shadow does not touch the owner’s original session; side effects: visible in tmux ls, needs cleanup on exit; mechanism inferred from man, unmeasured). If it holds, TODO §5’s multiple-windows item actually becomes easier on route B, since each app window gets its own current window.
  • Select & copy — copy-mode selection landing on the system clipboard via OSC 52. Demoted to a quick confirmation: the clipboard callback already exists in the package (code-read), so this will most likely just pass.
  • Attach a second, real terminal at the same time — feel the resize behaviour with two clients of different sizes.

All of it on an isolated -L server; nothing touches real sessions until the owner chooses to point the window at one. Two milestones: scrolling within minutes, then hanging off the Debug menu for daily use.
